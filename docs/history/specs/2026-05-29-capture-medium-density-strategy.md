# Capture Agent 中密度整理策略设计

## 背景

当前 Capture Agent 已经支持“长文分段阅读笔记 -> 最终整理稿”的技术路径，但触发阈值偏高：超过 `CAPTURE_SOURCE_CHAR_LIMIT` 才进入分段流程。实际测试中，一篇约 9,000 字的微信文章《生命是大模型，但不仅仅是大语言模型》被完整提取到了 raw archive，却只生成了约 900 字整理稿。问题不是没有读到全文，而是“总结全文核心内容”被理解成了短摘要，导致论证层次、关键案例和中段细节被压掉。

这份设计的目标是修正 Capture Agent 的默认整理策略：当用户说“总结全文”“总结核心内容”“提取重点”时，默认生成适合入库的中密度整理稿，而不是几句话摘要。

## 设计原则

1. 分档描述语义密度，不规定硬字数。
2. 微信回复保持短，只做审阅预览；完整整理稿保存在草稿和 Obsidian。
3. 对复杂文章保留主线、论证层次、关键概念、代表性例子、重要转折和最终判断。
4. 删除重复铺垫和口语冗余，但不删除支撑主线的细节。
5. 不强制固定模板，不要求“是什么 / 为什么 / 边界”等机械结构。
6. 硬编码只用于流程安全和触发条件，不用于写作风格。

## 意图密度分档

Capture Agent 在构造 `CaptureIntent` 时新增一个轻量字段，例如 `detail_level`。它不是输出模板，只是给 LLM 的整理密度提示。

### brief

适用于用户明确要求：

- “一句话总结”
- “简短摘要”
- “快速概括”
- “用几句话说”

输出目标：只保留结论和最核心理由。适合微信快速看，不适合作为默认 Obsidian 入库稿。

### medium

默认档。适用于用户要求：

- “总结全文”
- “总结核心内容”
- “提取重点”
- “整理一下”
- “这篇文章不错，总结一下”

输出目标：生成中密度整理稿。根据文章复杂度自然决定篇幅，保留文章主线、主要论证、关键概念、代表性例子、重要转折和最终判断。它应该是一篇可读笔记，而不是摘要 bullet list。

### deep

适用于用户明确要求：

- “详细整理”
- “深度总结”
- “尽量保留细节”
- “不要漏细节”
- “完整整理成笔记”

输出目标：保留更多分支、背景、案例、数字和论证细节。可以更长，但仍然不是逐段搬运原文。

## 默认解释规则

“总结全文核心内容”应解释为 `medium`，而不是 `brief`。

如果用户没有明确说“简短”“一句话”“几句话”，Capture Agent 不应把长文压缩成几句话。尤其是文章包含多个概念层、案例层或论证转折时，`medium` 必须覆盖这些层次。

如果用户点名关注某些部分，这些部分要提高权重，但不能让其他主线内容消失，除非用户明确说“只要”“仅保留”“删除其他”。

## 阅读覆盖策略

阅读策略和输出密度分开处理。

### 单次整理

短文章或结构简单文章可以单次整理。单次 prompt 仍应说明：

- 先内部判断用户真正想要的整理密度。
- 对 `medium` 默认保留论证层次和代表性例子。
- 不要输出内部计划、标签、目录或任务合同。
- 不要把全文压缩成几句话。

### 分段阅读再合成

当文章较长或结构复杂时，Capture Agent 应先生成分段阅读笔记，再合成最终整理稿。

技术触发可以先用长度近似判断，但这不是输出字数要求：

- 超过一个较低长文阈值时，例如约 8,000-10,000 字，优先分段阅读。
- 超过 `CAPTURE_SOURCE_CHAR_LIMIT` 时，强制分段阅读，避免只保留开头和结尾。
- 分段上限继续使用自然边界加硬上限：尽量按段落、标题、语义边界切，单段不能过大。

分段笔记只服务于最终整理，不直接展示给用户，不要求每段发明自己的文档结构。

## Prompt 边界

中密度整理 prompt 应表达质量目标，而不是字数目标。

推荐语义：

> 这不是几句话摘要。请根据材料复杂度决定篇幅；默认保留文章的主要论证层次、关键概念、代表性例子、重要转折和最终判断。删掉重复铺垫和口语冗余，但不要删掉支撑主线的细节。输出应是一篇自然可读的整理稿，不要机械套固定模板。

避免写法：

- “必须写 2000 字”
- “必须 8 个小标题”
- “每段都按是什么 / 为什么 / 边界”
- “必须包含目录纲要”
- “必须输出摘要、标签、参考来源”

## 微信与 Obsidian 的分工

微信消息有长度限制，因此微信首条回复仍只返回审阅预览：

- 标题
- 重点回应
- 简短总结
- 草稿编号和下一步指令

完整整理稿不塞进微信首条消息。用户需要看全文时，通过“展开草稿 / 看全文 / 继续看”分页查看。

Obsidian `captures/` 中保存的是中密度或深度整理稿，应该承担日常阅读、复习、检索和后续 Theme/Garden 提炼的职责。

## 回归样本

使用《生命是大模型，但不仅仅是大语言模型》作为回归样本。对于 `总结全文核心内容`，中密度整理稿至少应覆盖：

- 文章核心判断：生命是大模型，但不只是大语言模型，更接近物理时空世界模型。
- 序列化 AI 生物学范式的成就与局限。
- 从中心法则到时空法则的转向。
- 大语言模型与世界模型的分工：生成猜想与验证因果。
- 直觉与逻辑、系统 1 与系统 2 的类比。
- FlyWire / 虚拟果蝇连接组相关案例。
- 4D 全细胞模型相关案例。
- 工具决定论：测序、空间组学、成像、多模态数据工具决定模型上限。
- 最终判断：未来 AI 生物学要从预测生命走向运行生命。

这些覆盖点用于测试“没有被压成短摘要”，不是要求最终稿逐字使用这些标题。

## 测试策略

新增或更新测试时，应覆盖：

1. `总结全文核心内容` 被识别为 `medium`。
2. “一句话总结 / 简短摘要” 被识别为 `brief`。
3. “详细整理 / 尽量保留细节” 被识别为 `deep`。
4. 约 9,000 字复杂文章会触发分段阅读路径，而不是单次压缩。
5. 中密度 prompt 不包含硬字数要求，不包含固定模板要求。
6. 中密度 prompt 明确要求不要压成几句话，并保留论证层次、关键概念、代表性例子、重要转折。
7. 长文分段合成时，最终 prompt 接收分段笔记，而不是只读开头和结尾。
8. 微信 `chat_preview` 仍保持长度预算，不直接塞完整整理稿。

## 非目标

本设计不做以下事情：

- 不改变 raw archive 和 captures 的入库位置。
- 不增加额外 LLM 质量自检 pass。
- 不要求所有文章都走分段流程。
- 不把 Capture Agent 改成固定写作模板。
- 不在微信首条消息里返回完整整理稿。

## 成功标准

当用户发送一篇较长文章并说“总结全文核心内容”时：

- raw 原文完整保存。
- 草稿不是几句话摘要。
- 草稿能保留文章主要论证结构和代表性细节。
- 微信首条回复仍然短，但能说明草稿已生成，可展开查看。
- 用户回复“存库”后，Obsidian `captures/` 中的笔记可以作为日常阅读和后续 Theme/Garden 提炼的可靠材料。
