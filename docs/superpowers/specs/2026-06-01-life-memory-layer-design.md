# Hermes Life Memory Layer Design

Date: 2026-06-01

## 定位

Life Memory Layer 是 Life Assistant 的个性化记忆层。它不负责替代 Life 的事件记录、提醒规则、日报和周报，而是从这些长期数据和用户反馈里提炼出更稳定的生活模式，让 Life Assistant 更会判断：

- 什么时候该提醒。
- 提醒应该多强。
- 应该用什么语气。
- 哪些建议已经说腻了，需要换策略。
- 当前阶段有什么临时生活目标或例外状态。

知识库管理暂时不作为记忆层重点。Capture、RAG、Review、Garden 里的强约束应该写进提示词和工具合同，不能依赖记忆命中。Knowledge 只共享少量全局交互偏好，例如微信长内容用文件、不要让用户记编号、先预览再确认。

## 目标

- 让 Life Assistant 从“固定规则提醒器”进化成“会根据用户生活节奏调整的助手”。
- 自动学习用户的作息、饮食、喝水、久坐和提醒响应模式。
- 自动调整提醒时机、提醒强度和文案风格，减少无效打扰。
- 支持阶段性目标和例外状态，例如最近调睡眠、出差、生病、加班。
- 让用户可以随时查看、删除、禁用记忆，但不要求用户逐条审批。
- 保持 Life 数据和 Knowledge 数据隔离，避免生活隐私进入知识库 Agent。

## 非目标

- 不做医疗诊断、疾病判断、用药建议或治疗方案。
- 不把 Life 记忆写入 Obsidian 知识库。
- 不让用户每条记忆都确认。记忆应该自动形成，用户只在需要时审阅或撤销。
- 不把所有聊天内容都自动沉淀成长期记忆。
- 不用记忆承载系统硬规则。硬规则仍然写在提示词、工具描述和代码里。
- P1 不接 Apple Health、手表、手机传感器或营养数据库。

## 核心原则

### 记忆不等于记录

记录是“今天 13:20 吃了午饭”。记忆是“用户最近两周常常 13:30 以后才吃午饭，如果超过 14:00 还没记录午餐，晚餐节奏容易被影响”。

Life Memory 应该尽量保存模式和偏好，而不是复制事件流水。

### 自动形成，透明可控

默认自动形成记忆，不打断用户确认。用户可以随时问：

- 你现在记住了我什么？
- 为什么刚才这么提醒我？
- 删掉关于睡眠提醒语气的记忆。
- 暂时别用饮食记忆提醒我。

### 记忆有强弱和时效

不是所有记忆都永久生效。系统应区分稳定偏好、弱推断、阶段目标和短期例外。

### 先少而准，再变聪明

P1 不追求复杂人格画像。优先做三个高价值闭环：

- 作息记忆。
- 饮食/喝水记忆。
- 提醒反馈记忆。

## 记忆类型

### 生活规律记忆

从 Life 事件和提醒日志自动统计形成。

例子：

- 用户最近 14 天常见入睡区间是 00:30-01:30。
- 用户工作日午餐记录经常晚于 13:30。
- 用户下午 15:00-17:00 更容易出现长时间久坐。
- 用户周日晚上更容易拖延睡觉。

用途：

- 决定提醒时间。
- 识别异常偏离。
- 周报里解释生活趋势。

### 提醒响应记忆

从提醒是否被响应、是否被忽略、是否被暂停形成。

例子：

- 22:45 的睡前收尾提醒比 23:30 的睡觉提醒更有效。
- 喝水提醒如果一天超过 3 次，用户更容易忽略。
- 久坐提醒需要直接一点，普通语气容易被略过。

用途：

- 调整提醒频率。
- 调整提醒强度。
- 避免重复说无效废话。

### 文案偏好记忆

从用户反馈和长期交互里形成。

例子：

- 用户不喜欢鸡汤式提醒。
- 用户喜欢直接、克制、有依据的表达。
- 用户不喜欢被要求回复复杂编号。
- 微信消息应该短，长内容走文件或 Dashboard。

用途：

- 生成更像“懂你的人”的提醒。
- 避免提醒本身造成压力或反感。

### 阶段目标记忆

用户明确表达或系统从近期任务里识别出的短期生活目标。

例子：

- 这周优先把睡眠调回来。
- 最近减少久坐，比运动量更重要。
- 最近胃不舒服，饮食提醒要保守。

用途：

- 在提醒排序里提高相关目标的优先级。
- 周报围绕当前目标复盘。
- 过期后自动淡出，避免长期污染。

### 例外状态记忆

短期上下文，不应长期生效。

例子：

- 今天出差。
- 今晚加班。
- 这两天身体不舒服。
- 周末不按工作日节奏提醒。

用途：

- 暂时降低提醒强度。
- 暂停不合适的提醒。
- 避免按平常节奏误判用户。

## 记忆状态

每条记忆都应带状态，避免“一旦记住就永久支配行为”。

- `active`：稳定生效，Agent 默认使用。
- `weak`：弱推断，只作为参考，不能强制改变行为。
- `temporary`：阶段性或例外状态，有明确过期时间。
- `archived`：历史保留，不再生效。
- `blocked`：用户明确否定过，不再使用同类记忆。

## 记忆如何被使用

### 选择提醒时机

系统先用规则判断“是否可能需要提醒”，再用记忆判断“现在是不是好时机”。

例子：

- 固定规则：午餐提醒窗口是 11:30-14:00。
- 记忆调整：用户平常 13:20 左右吃饭，所以 12:00 不急着提醒；如果 14:00 仍无记录，再提醒。

### 调整提醒强度

提醒强度不应固定。它应由风险、连续忽略次数、当前目标和用户偏好共同决定。

强度示例：

- 轻提醒：记得喝点水。
- 中提醒：你今天到现在水量偏少，先喝一杯再继续。
- 强提醒：你已经连续久坐很久了，先离开电脑 5 分钟，回来再继续。

### 避免重复无效策略

如果同一种提醒长期无效，系统不应继续重复，而应换策略。

例子：

- 连续多天睡前提醒无效，不再只说“早点睡”。
- 改成更早的“收尾提醒”：现在开始收尾，别把睡觉拖成临时决策。

### 个性化文案

LLM 可以根据记忆生成文案，但不能编造事实。它只能使用 fact pack 里的事实和 memory pack 里的偏好。

文案应克制、短、直接。Life Assistant 可以有一点人味，但不要装作医生，不要制造焦虑。

### 周报解释

周报不只列数据，还要利用记忆解释模式。

例子：

- 这周运动少不是核心问题，真正影响节奏的是连续晚睡导致白天能量下降。
- 午餐记录偏晚集中在高强度工作日，建议先处理午间中断，而不是泛泛要求“饮食规律”。

### 生活实验

Life Assistant 可以把提醒策略当成小实验。

例子：

- 本周测试 22:45 睡前收尾提醒。
- 如果 3 次里有 2 次有效，下周继续。
- 如果无效，改成更早或更弱的提醒。

这不是用户要管理的实验，而是系统内部调整策略的依据。

## 数据模型方向

P1 推荐继续使用 SQLite，新增独立 `life_memory_*` 表。不要复用 Knowledge 表。

### `life_memory_items`

存储当前可用记忆。

字段方向：

- `id`
- `domain`: `life.sleep`、`life.meal`、`life.water`、`life.sedentary`、`life.copy`
- `memory_type`: `pattern`、`response`、`copy_preference`、`stage_goal`、`exception`
- `status`: `active`、`weak`、`temporary`、`archived`、`blocked`
- `content`
- `confidence`: `low`、`medium`、`high`
- `evidence_json`
- `source`: `event_stats`、`reminder_feedback`、`user_statement`、`weekly_review`
- `effective_from`
- `expires_at`
- `last_used_at`
- `created_at`
- `updated_at`

### `life_memory_observations`

存储形成记忆前的观察，不直接驱动 Agent。

例子：

- 最近 7 天午餐记录 5 次晚于 13:30。
- 最近 3 次 23:30 睡觉提醒均未收到响应。

用途：

- 支撑记忆置信度。
- 调试系统为什么形成某条记忆。
- 防止凭一次事件就过度学习。

### `life_memory_hits`

记录某次提醒或周报用了哪些记忆。

字段方向：

- `id`
- `memory_id`
- `used_by`: `life_tick`、`daily_review`、`weekly_review`、`record_life_event`
- `target_id`
- `used_at`
- `effect_json`

用途：

- 回答“为什么刚才这么提醒我？”
- 评估某条记忆是否真的有用。
- 发现错误记忆并降权。

## 运行流程

### 记忆生成流程

1. `life_tick`、日报或周报构建 Life fact pack。
2. deterministic analyzer 从事件和提醒日志中生成 observations。
3. memory consolidator 把重复出现、证据足够的 observations 合并成 memory items。
4. 低置信记忆进入 `weak`。
5. 高置信且低风险记忆进入 `active`。
6. 阶段目标和例外状态进入 `temporary`，必须有过期时间。

P1 的 analyzer 应尽量确定性实现。LLM 可以用于周报文字表达，不应负责凭空决定核心记忆。

### 提醒决策流程

1. 规则层判断候选提醒。
2. 读取相关 Life 事件、提醒日志和 active/weak/temporary memories。
3. 构建 reminder decision pack。
4. deterministic policy 决定是否提醒、提醒强度、是否降噪。
5. LLM 只负责把决策写成合适的短文案。
6. 写入 reminder log 和 memory hits。

### 用户反馈流程

用户不需要主动维护记忆，但自然语言反馈应能影响记忆。

例子：

- “别老提醒我喝水” -> 降低喝水提醒频率，生成或更新 copy/frequency preference。
- “这种提醒太鸡汤了” -> 生成文案偏好记忆。
- “这周先盯睡眠” -> 生成 temporary stage goal。
- “今天加班，别提醒睡觉” -> 生成 temporary exception。

## 工具和接口方向

P1 可以新增或扩展 Life 工具：

- `life_memory_review()`：查看当前 Life 记忆摘要。
- `life_memory_forget(query)`：删除或禁用匹配记忆。
- `life_tick()`：读取记忆后做提醒决策。
- `record_life_event()`：记录事件，同时捕捉明确反馈。

用户不需要常用这些工具。它们主要给 Hermes 主 Agent 在必要时调用。

## 安全和边界

- 健康相关记忆必须是生活方式层面的，不能形成疾病判断。
- 敏感事实默认不进入全局记忆。
- Life 记忆只给 Life Agent 使用，不给 Knowledge Agent 做 RAG。
- 任何基于记忆的判断都应能解释来源。
- 用户明确否定的记忆必须能进入 `blocked` 或 `archived`。
- 临时状态必须有过期时间，避免永久影响提醒策略。

## P1 范围

P1 只做最小有价值闭环：

1. 作息记忆
   - 学习常见睡眠/起床区间。
   - 支持睡前收尾提醒调整。

2. 饮食和喝水记忆
   - 学习常见漏餐/晚餐/喝水不足时段。
   - 调整提醒时间和频率。

3. 提醒反馈记忆
   - 记录哪些提醒被响应、忽略、暂停。
   - 避免重复无效提醒。

4. 记忆审阅和删除
   - 支持“你记住了我什么？”
   - 支持“删掉/别用某条记忆”。

## P2 方向

- 更细的生活实验策略。
- 将周报建议和下周提醒策略联动。
- Dashboard 展示记忆形成依据和使用记录。
- 更复杂的阶段目标管理。
- 引入 Apple Health 或可穿戴设备数据后，重新校准记忆置信度。

## 测试策略

后续实现计划应覆盖：

- 连续多天事件能形成生活规律记忆。
- 单次偶发事件不能直接形成 active 记忆。
- 临时例外状态会过期。
- 提醒决策能读取记忆并调整时机。
- 用户反馈能更新提醒频率或文案偏好。
- 用户能查看和删除记忆。
- Knowledge Agent 不会读取 Life 记忆。
- 周报能引用记忆解释趋势，但不做医疗诊断。

## 成功标准

第一版成功不是“记住很多东西”，而是用户能明显感觉到：

- 提醒更少废话。
- 提醒时机更贴近真实生活节奏。
- 文案更像 Hermes 认识我，而不是通用健康机器人。
- 周报能解释模式，而不只是罗列数据。
- 出现错误记忆时，我能看见并删掉它。
