# Hermes Knowledge Product Redesign

更新日期：2026-06-14

## 1. 背景

Hermes Knowledge 已经具备一批知识库能力：Capture、Library、RAG、Theme、Garden、Canvas、Review、Reading Session 和前端 Knowledge Chat。当前问题不是能力不足，而是产品形态变散：用户会看到许多 Agent、工具和视图，但不容易感到“这就是我日常读材料、理解材料、沉淀材料的自然工作流”。

这次改版的目标不是先做面试演示，也不是继续堆功能，而是把产品收束成一个自己长期可用、可维护、可解释的知识工作流。演示价值应来自真实好用的闭环，而不是单独包装出来的展示壳。

## 2. 产品定位

Hermes Knowledge 是一个面向 AI、产品、研究类知识工作者的阅读理解与知识沉淀助手。

它解决的问题是：

- 收藏材料后容易沉没；
- 长文章、PDF、公众号、截图等材料读起来费劲；
- 读材料时产生的追问和理解很难回流到长期笔记；
- 后续问知识库时，答案容易没有来源、不可追溯；
- 传统知识库要求用户提前分类、手动整理，维护成本过高。

新版核心闭环：

```text
材料进入 -> 阅读讨论 -> 用户确认沉淀 -> 自动结构维护 -> 可追溯问答/复用
```

产品原则：

- 用户不需要理解一堆 Agent 名字。
- 重要写入必须经过用户确认。
- Raw 永远是原始归档，不被改写。
- Capture 是主笔记，不是随手摘要。
- Knowledge Cards 只保存可复用知识，不为每篇材料强行生成。
- 长输出走前端或文件，不强塞进微信。
- 所有长期结论都要能追到来源。

## 3. 核心用户流程

### 3.1 材料进入

用户可以从微信或前端发送：

- 公众号链接；
- 小红书图文；
- 普通网页链接；
- Markdown、PDF、Word、txt 等文件；
- 图片或截图；
- 直接粘贴文本。

系统应先识别用户意图，而不是默认总结。

主要意图：

- 全文保存：原文一字不改进入主 Capture，可附加必要目录或元信息；
- 精炼总结：压缩材料，保留主线和关键细节；
- 重点提取：围绕用户点名关注的问题展开；
- 阅读讨论：围绕材料中的某个概念、段落或疑问多轮解释；
- 入库整理：把已有讨论整理成笔记或卡片。

### 3.2 阅读讨论

Reading Session 是新版主体验。

当用户不是明确要求“生成草稿/入库”，而是在问“这段什么意思”“这里为什么重要”“和我之前看的东西有什么关系”时，系统应创建或恢复围绕当前材料的 Reading Session。

Reading Session 行为：

- 绑定当前文章、文件、截图、摘录或已入库 Capture；
- 保存多轮问题、回答、轻量证据和当前焦点；
- 可以同时使用原文、知识库和必要外部资料回答；
- 不自动写 Obsidian；
- 用户说“整理进笔记”时才进入沉淀流程。

回答要求：

- 先回答好问题，不暴露复杂检索过程；
- 必要时标注来源来自原文、知识库或外部资料；
- 没有依据的判断应以解释或推测口吻表达；
- 微信回复保持短，长解释可引导到前端或文件。

### 3.3 用户确认沉淀

当用户说“整理进笔记”“存起来”“做成卡片”时，如果输出形态不明确，系统应短问：

```text
你想整理成哪种？
1. 原文增强版主笔记：保留文章主线，把刚才讨论补进去
2. 局部学习笔记：只整理这次卡住的概念/段落
3. 知识卡片：提炼成以后可复用的观点、方法、事实或风险
```

规则：

- 选择只对本次生效，不写成长期默认；
- 任何写入前都先生成草稿；
- 用户确认后才写入 Obsidian 和数据库；
- 修改主 Capture 前要备份旧版本；
- Raw 不被改写。

### 3.4 自动结构维护

Library 是后台卫生系统，不应作为用户显性 Agent 强调。

它负责：

- DB 与 Obsidian 文件一致性；
- Capture/raw properties 补全；
- 长文目录纲要；
- 无 Markdown 标题长文的结构切分；
- identity embedding；
- section embedding；
- 重复草稿、垃圾文件、断链引用的维护；
- 入库后自动对当前材料做定向维护。

用户只需要感知：

- “入库后系统会自动整理结构和索引”；
- “全库维护可以手动触发，并会有备份和报告”。

### 3.5 可追溯问答

RAG 是复用能力。

用户问知识库问题时，系统应：

- 从 captures、sections、Knowledge Cards 和必要的结构关系中找材料；
- 优先使用真正命中的内容，而不是展示一堆候选；
- 长文只读取相关章节；
- 回答中显示可读来源标题；
- 参考来源只列实际使用的材料；
- 用户追问“展开一点/继续”时沿当前上下文继续。

前端 Knowledge Chat 应成为 RAG 和 Reading Session 的满血入口，支持更长回答、文件上传、完整引用和长报告。

## 4. 功能取舍

### 4.1 保留并强化

#### Capture

定位：材料进入与草稿生成。

重点改法：

- 不再把所有材料默认压缩成总结；
- 明确支持全文保存、精炼总结、重点提取、原文增强版；
- 对用户点名关注点加强意图理解；
- 文件输入与微信输入行为一致；
- 草稿预览短而可审阅，长文通过展开、文件或前端查看。

#### Reading Session

定位：围绕单份材料的多轮阅读理解。

重点改法：

- 绑定当前材料和讨论状态；
- 支持原文、知识库、外部资料混合回答；
- 讨论不自动入库；
- 整理时根据用户意图转成主 Capture、局部学习笔记或 Knowledge Card。

#### Library

定位：后台维护和索引。

重点改法：

- 入库后自动维护当前材料；
- 手动全库维护时清晰报告；
- 可自动修的元数据不要丢给用户手动修；
- 保持 DB、captures、raw、embedding 一致。

#### RAG

定位：基于知识库的可信问答。

重点改法：

- 来源标题可读；
- 引用只列实际使用来源；
- 长答案支持文件或前端；
- 多轮追问沿当前检索上下文继续。

#### Theme

定位：Obsidian 原生结构层，用 `themes/*.md` 维护跨材料的主题关系地图。

重点改法：

- Theme Agent 自动生成/更新 `themes/*.md`；
- Theme 页是 MOC 风格的关系地图，帮助人阅读多篇材料之间的联系；
- Theme 可提出可沉淀为 Knowledge Cards 的方向；
- Theme 不成为 Garden Card 容器，也不单独做前端管理页；
- Theme 页只更新 Hermes 托管区，保留用户手写的 `## 我的补充`。

#### Knowledge Cards

定位：可复用知识对象，不是文章摘要。

Garden 目录可以保留，但用户文案中应逐步改叫 Knowledge Cards。

### 4.2 弱化或隐藏

#### Canvas / 画板

Canvas 从主线移除。

原因：

- 当前视觉质量不稳定；
- 用户理解成本高；
- 容易从“阅读与沉淀”跑偏到“知识图谱展示”；
- 对核心闭环不是必需。

处理方式：

- 隐藏或下线显性入口；
- 已有文件不强删；
- 后续只有当 Knowledge Cards 足够多且关系真实清晰时，再考虑新的可视化方案。

#### Review

Review 暂时作为二线能力。

保留方向：

- 每天讲一个知识点；
- 记录阅读次数或复习次数；
- 支持围绕刚讲过的点追问。

但它不是本轮改版的主线。

## 5. Knowledge Cards 改版

### 5.1 定义

Knowledge Card 是从材料、阅读讨论或多篇笔记中提炼出的可复用知识对象。

它不是：

- 每篇文章的摘要；
- 自动生成的观点；
- 复杂知识图谱节点；
- MOC 的替代品。

它应该满足：

- 离开原文也有复用价值；
- 能追溯到来源；
- 足够短，适合以后快速调用；
- 支持被 RAG 和前端看板检索。

### 5.2 类型

只保留 4 类：

- `viewpoint`：观点、判断、解释框架；
- `method`：方法、流程、策略、操作步骤；
- `fact`：重要事实、案例、数据、事件、benchmark；
- `risk`：风险、误区、边界、反例、注意事项。

不单独保留 `question` 类型。开放问题可以作为卡片正文中的一节，也可以留在阅读讨论里，避免类型过多。

### 5.3 生成规则

- 用户明确要求“做成卡片/提炼可复用内容”才生成；
- 系统可在材料明显有价值时建议，但不自动写入；
- 类型由系统推断，用户不需要先分类；
- 命中重复或相似卡片时，优先提示已有卡片；
- 用户可以选择更新已有卡片或新建；
- 卡片必须显示来源材料标题和 Obsidian 链接。

### 5.4 卡片内容

卡片应保持人能读懂，而不是模板痕迹过重。

统一结构建议：

```markdown
# 标题

一句话说明这张卡片讲什么。

## 内容

根据卡片类型自然组织，不强行套“是什么/为什么/边界”。

## 适用或启发

说明以后什么时候会用到它。

## 来源

- [[来源材料标题]]
```

不同类型只影响写作倾向，不强制不同模板。

## 6. 前端改版

前端不是替代 Obsidian，而是让长内容和复杂操作更好用。

第一版只做 3 个核心页面。

### 6.1 Knowledge Workbench

用途：

- Chat Mode：满血聊天、文件上传、RAG、Reading Session、长回答；
- Draft Review Mode：查看整理稿、原文、元信息，继续修改并确认入库；
- Source Mode：查看完整原文、OCR 或文档提取文本；
- Result Mode：查看长答案、导出报告和完整引用。

关键体验：

- 和微信入口共用后端工具；
- 不受微信字数限制；
- 能显示当前绑定材料；
- 能显示来源、工具调用和材料状态；
- 草稿审阅不再是单独主页面，而是 Workbench 里的 Draft Review Mode。

### 6.2 Knowledge Cards Board

用途：

- 浏览沉淀后的卡片；
- 按观点、方法、事实、风险分组；
- 查看来源材料；
- 找到最近生成和最近使用的卡片。

关键体验：

- 卡片显示 summary，而不是长全文；
- 点击进入详情；
- 来源材料总是可见；
- 不显示无意义内部 id。

## 7. 内部模块边界

用户侧不强调 Agent 名字，内部保留清晰模块：

- `Capture`：材料提取、意图整理、草稿生成；
- `Reading`：围绕单份材料的多轮讨论；
- `Library`：结构维护、索引、一致性；
- `Theme`：跨材料关系发现，自动维护 Obsidian `themes/*.md`；
- `RAG`：知识库问答和引用；
- `Cards`：Knowledge Cards 草稿、去重、入库。

Theme 是可见的 Obsidian 结构层，但不单独占用前端页面。Canvas 暂时退出主线。

## 8. 实施阶段

### P0：收口主线

目标：停止功能扩散，让主 Agent 不再主动把用户带向 Canvas，同时让 Theme 回到 Obsidian 主题地图的位置。

任务：

- 更新工具描述和系统提示；
- 隐藏 Canvas 主入口；
- Theme 自动维护 `themes/*.md`，但不新增独立前端 Theme 页面；
- 明确用户可见主能力：读材料、讨论、入库、问答、卡片沉淀。

验收：

- 用户问“整理知识库/扫描关联”时，优先生成或更新 Theme 主题页，而不是推荐 Canvas；
- 用户普通问答不会暴露 Theme/Garden 等内部术语；
- 主 Agent 回复更像产品功能，而不是工具清单。

### P1：跑通 Reading -> Capture/Card

目标：用户读材料时的讨论能自然沉淀。

任务：

- 文件、链接、截图、已入库 Capture 都能创建或恢复 Reading Session；
- 多轮追问绑定当前材料；
- “整理进笔记”时反问 3 种沉淀形态；
- 原文增强版写回主 Capture 前备份；
- 局部学习笔记和 Knowledge Card 走草稿确认。

验收：

- 用户发文章问概念，系统不误生成 Capture 草稿；
- 多轮讨论后可整理成主 Capture；
- Raw 不被改；
- 草稿确认后 DB 和 Obsidian 一致。

### P2：Knowledge Cards 改版

目标：让 Garden 从“观点生成器”变成可复用知识卡片库。

任务：

- 用户文案改为 Knowledge Cards；
- 卡片类型收束为 viewpoint/method/fact/risk；
- 生成前做重复检查；
- 支持更新已有卡片；
- 卡片来源显示可读标题和 Obsidian 链接。

验收：

- 同一主题重复生成不会产生重复卡；
- 卡片不再出现裸 id；
- 用户能看懂每张卡片以后有什么用；
- RAG 能检索并引用卡片。

### P3：前端工作台

目标：把微信做不好的长内容操作放到前端。

任务：

- Knowledge Chat 重命名或定位为 Knowledge Workbench；
- Draft Review 合并进 Workbench，不再作为主导航里的独立页面；
- Workbench 支持文件上传、长回答、草稿审阅、原文查看、引用和工具状态；
- Knowledge Cards Board 支持分类浏览和详情页；
- 前端调用已有后端能力，不新造一套逻辑。

验收：

- 一篇长 PDF 可以在前端上传、讨论、整理；
- 草稿可以在前端完整审阅；
- 主导航不再把 Capture Review 作为独立知识工作流；
- 卡片能按类型浏览并追到来源。

### P4：稳定性与可观测性

目标：长期自用时可排查、可恢复。

任务：

- 关键工具调用写入 run ledger；
- 失败时显示用户能理解的状态；
- 备份、报告、文件输出路径清晰；
- 数据清理工具默认 dry-run；
- 定期检查 DB 和 Obsidian 一致性。

验收：

- 出错能查到是哪一步失败；
- 清理前有备份；
- DB capture 数量与文件数量一致；
- 长输出不会丢在微信截断里。

## 9. 非目标

本轮不做：

- 自动为所有文章生成卡片；
- 自动生成 Canvas；
- 复杂知识图谱编辑器；
- 新增单独的 Theme 前端管理页；
- 完整 Review 系统重做；
- 为面试单独做假数据或假流程。

## 10. 成功标准

这版完成后，用户应能自然完成以下任务：

1. 发一篇材料，让 Hermes 解释读不懂的地方。
2. 多轮讨论后，把理解整理回主笔记或单独知识卡片。
3. 入库后系统自动维护结构和索引。
4. 过几天再问相关问题，Hermes 能引用这篇材料和相关卡片回答。
5. 在前端查看长回答、完整草稿和卡片来源。

如果这 5 件事顺畅，Hermes Knowledge 就从“工具合集”变成了一个可用产品。
