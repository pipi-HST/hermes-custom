# Hermes 产品重构故事：从「收藏夹」到「认知内化工作台」

> 这份文档是 AI 产品经理面试的项目主叙事（Portfolio Narrative）与问答脚本。
> 配套可运行数据：`python scripts/seed_interview_demo.py`（Golden Demo Dataset）。

---

## 口径说明（2026-11）

这份文档保留“当时为什么这么改”的历史，但面试口径以本节为准：

- **产品形态**：当前 Hermes 是 Web-native 三栏工作台（左侧资料定位，中间阅读/审阅，右侧来源与 AI 辅助），配自研卡片板（Cards Board）和知识图谱。Obsidian 只作为可选的 Markdown 导出/外部编辑兼容，不是主界面，也不是存储真相。
- **卡片类别只有四类**：洞察/金句、新知/概念、方法/框架、避坑/边界。Golden Demo 预置 9 张卡片，不是“九类模板”。
- **主链路**：资料 → 卡片 → 专题；检索先证据后卡片（evidence-first），卡片可以按来源数与引用数加权，但不能无条件置顶。
- **检索证据**：真实 DashScope 重跑已于 2026-11-16 完成（`docs/BENCHMARK-RAG-V3-dashscope.md` / `docs/benchmark-rag-v3-dashscope.json`）：G0 旧版字面基线 Recall@5 = 0.389，G1–G2 = 0.833，G3 = 1.0（卡片级召回 6/6），负样本 G0 10/10、G1–G3 9/10（q24 漏过一条）；只能表述为“本语料（28 query，18 正 + 10 负）上的语义召回增益”，不能外推。离线 hash post-fix 四组 0.389、负样本 10/10（`docs/BENCHMARK-RAG-V3-offline-postfix.md`）仍保留为字面回归基线。G0 dispatcher 修复前的旧 0.833 报告已作废；新数字是修好 G0 与卡片 query embedding 后独立重跑的结果，两者不要混用。
- **数字规则**：正文中的评测数字必须能指到 docs 下的 JSON/Markdown 产物；没有产物的数字标“待重跑/待补 artifact”，不当作当前证据。

## 一、产品定位

**一句话定位**：Hermes 是一个面向高频学习者的「资料 → 卡片 → 专题」认知内化工作台。它不只帮用户保存内容，而是让每一次输入都变成可回看、可复用、可组合的个人判断。产品主界面是 Web-native 三栏工作台，配自研卡片板与知识图谱；Obsidian 只是可选的 Markdown 导出兼容。

**目标用户**：AI 产品经理、研究者、咨询顾问、需要持续跨领域学习的知识工作者。

**核心场景**：

1. 通勤时看到一篇公众号好文，想快速判断值不值得读，并在读完后留下自己的判断。
2. 面试前需要把过去积累的行业拆解、方法论和踩坑复盘快速组织成回答框架。
3. 读到一个没看懂的概念，希望有人围绕原文陪读解惑，而不是把整篇文章塞进收藏夹。
4. 长期追踪 3–5 个专题（如 Agent 架构、AI 产品面试），希望看到资料、卡片和观点之间的关系。

**对外三个概念**（刻意保持极简，避免内部术语泄漏）：

- **资料（Notes）**：原文与整理稿，是证据层，必须保真。
- **卡片（Cards）**：从资料中提炼的可复用认知，分为洞察/金句、新知/概念、方法/框架、避坑/边界四类。
- **专题（Topics）**：围绕长期问题组织的资料与卡片集合。

## 二、重构前的问题：四个核心痛点

### 痛点 1：保存动作被「AI 整理」劫持，原文越存越短

**现象**：用户点保存，系统却调用大模型把正文改写成一篇「更通顺」的摘要；长文被压缩，案例、数字和限定条件丢失。用户回看时找不到原始论证，只能重新去翻公众号。

**根因**：保存与整理被绑定在同一条同步链路里，`body_markdown` 直接采用 LLM 输出，缺少保真校验；前端快速新建笔记也默认触发 AI 组织。

**重构方案**：

- 明确「保存 = 保真」：原始材料写入 `raw_text` 与 `_archive/raw/` 证据层，永不覆盖。
- 新增编辑稿保真护栏：若 LLM 结果相比用户原文保留不足 90%，或实质性段落保留率低于 75%，自动回退到用户原文，并在建议中加入警告。
- 快速手动笔记默认 `organize=False`，不触发同步 LLM；需要 AI 建议时由用户显式开启。
- 仅在用户明确要求「提炼观点 / 核心导读」时，生成 `## 💡 AI 核心导读` 置于顶部，原文完整保留在下方 `## 原文`。

**结果**：用户保存的正文不再被意外压缩；AI 只补充导读、摘要、标签和分类建议。

### 痛点 2：多级 Agent 的「传话筒效应」让答案不可追溯

**现象**：检索 Agent 把十篇材料压成摘要，分析 Agent 再压成三条结论，写作 Agent 只看到二手转述。最终答案结构完整、语气专业，却找不到原文依据。

**根因**：Agent 之间用自然语言摘要交接，每一层都在做有损压缩，且下游没有回查原始证据的权限。

**重构方案**：

- 建立共享证据层：所有 Agent 通过 capture/section ID 读写同一份原始材料。
- 交接结构化：任务目标、必须保留的约束、可用证据 ID、允许推断范围、失败回退策略。
- 原始材料旁路：最终写作与评审必须能回查原文，而不是只信上游摘要。
- 评测加入「证据保真率」抽查，不只看答案像不像。

**结果**：错误可归因到检索、规划或写作，而不是笼统归咎于「模型不行」。

### 痛点 3：重型 Research 管线延迟过高，反思环边际收益递减

**现象**：七阶段 Research 管线经常打满 130 秒超时预算，用户在前 30 秒大量流失；离线评分却只从 3.9 提升到 4.0。

**根因**：串行检索、全量证据筛选、固定反思与二次修订；流程完整优先于用户感知。

**重构方案**：

- 并行化互不依赖的来源检索，统一超时与降级。
- 分层筛选：规则去重 → 小模型粗筛 → 大模型精排。
- 缓存稳定的中间产物（查询改写、网页摘要、实体归一化），带 TTL 与版本。
- 早停：证据覆盖达标即停止扩充；初稿通过结构检查即跳过二次修订；高置信问题走轻量链路。

**结果**：早期内部记录（未归档）曾显示分段延迟下降；当前唯一可复现的是轻量链路单例 21.3–27.2 秒（§8.11/§8.12，不是 P50/P95）。Token -46% 与人工评分 4.0 没有归档评测产物，面试时标“待复核”，不作为当前证据。

### 痛点 4：知识库只有「收藏」，没有「内化」

**现象**：用户存了上千篇，却说不清自己有什么观点；检索能返回相似片段，却无法支持面试表达或方案输出。

**根因**：产品把知识等同于文档，缺少卡片层与专题层；收藏与复习、输出之间没有闭环。

**重构方案**：

- 资料层保真，卡片层提炼，专题层组织长期问题。
- 四类卡片模板：洞察/金句、新知/概念、方法/框架、避坑/边界。
- 知识图谱连接「卡片—资料」「卡片—卡片」「专题—资料」「资料—资料」。
- 专题检索直接服务面试与方案输出，而不是只返回文档列表。

**结果**：Golden Demo 数据集包含 6 篇资料、9 张卡片、3 个专题、36 条图谱边（以 `scripts/seed_interview_demo.py` 的输出校验为准），打开即可演示完整闭环。

## 三、架构与关键取舍

### 1. SQLite + Markdown 双存储

**选择**：SQLite 保存路由、状态、索引和图谱；Markdown 保存正文与 frontmatter。

**取舍**：

- 优点：资料正文可读、可迁移、可用 Obsidian 等工具打开；卡片、专题、图谱和审阅状态在 DB 中可直接查询。
- 代价：必须明确真相边界——资料正文以 Markdown 为源，卡片/专题/图谱以 DB 为源；只有资料正文能由文件重建，DB 中的结构化对象不能仅靠 Markdown 恢复，必须备份数据库。
- 结论：个人知识库的第一优先级是「数据属于用户」，因此接受工程复杂度，但不把 DB 和文件混成同一个真相。

### 2. 同步保存，异步增强

**选择**：保存动作只做提取、清洗、落库与原文归档；摘要、标签、嵌入、图谱刷新尽量异步或按需。

**取舍**：

- 优点：保存延迟可预期，用户不会因为模型慢而丢失输入。
- 代价：首次检索可能暂时没有向量，需要索引状态提示与后台补齐。
- 结论：写入路径的确定性优先于「一次到位」的智能。

### 3. 本地优先的确定性向量（Golden Demo）

**选择**：Demo 数据用 numpy 按主题/关键词种子生成 1024 维归一化 float32 向量，离线即可完成相似度检索与图谱连边。

**取舍**：

- 优点：无 API Key 也能演示；结果可复现；相似主题余弦相似度高。
- 代价：不代表真实语义模型的召回质量，只用于产品流程验收。
- 结论：Demo 与生产解耦，真实环境仍使用 DashScope `text-embedding-v4`。

### 4. 四大意图路由，而不是「看到链接就入库」

**选择**：WeChat / Supervisor 层严格区分伴读解惑、好文收集、沉淀卡片、专题检索。

**取舍**：

- 优点：避免讨论内容污染资料库；用户心智清晰；减少无效写入。
- 代价：需要更精确的意图识别与澄清策略。
- 结论：宁可短问一句，也不要把「讨论」误存成「资料」。

### 5. 防传话筒铁律

**选择**：工具参数必须原封不动传递用户 URL / 原文；禁止模型在生成参数时缩写或改写。

**取舍**：

- 优点：从入口保证证据完整，后续所有整理都有可靠源头。
- 代价：长消息会占用更多上下文与存储。
- 结论：上下文成本可以优化，证据丢失不可逆。

### 6. Web-native 三栏工作台 + 自研卡片板与知识图谱

**选择**：主界面是 Web 三栏工作台：左侧资料定位，中间阅读/审阅，右侧来源与 AI 辅助。卡片板独立承载已确认卡片的筛选、详情和来源；知识图谱负责局部关系浏览。

**取舍**：

- 优点：资料、草稿、卡片、专题在同一个产品界面里闭环，卡片和关系是一等对象，不再依附 Obsidian 插件或 Canvas 文件。
- 代价：前端要自己维护三栏状态、卡片筛选和图谱布局，工程量高于“把 Markdown 丢给 Obsidian”。
- 结论：Obsidian 可以是可选的 Markdown 导出/外部编辑兼容，但不能成为产品主界面和存储真相。

> 历史：早期版本确实依赖过 Obsidian Canvas 和 MOC 主题页；这条路线已退役，保留在附录 A 作为设计演进记录。

## 四、STAR 面试问答脚本

### Story 1：保存被 AI 压缩（痛点 1）

**S（情境）**：用户反馈「存进去的文章变短了，案例和数字都不见了」，客服每周收到多起类似投诉。

**T（任务）**：在不牺牲 AI 整理价值的前提下，保证用户原文永不丢失。

**A（行动）**：

1. 把保存链路拆成「原文归档」与「可编辑整理稿」两层，原文写入 raw 证据层。
2. 在编辑稿生成处加保真护栏：长度保留率 < 90% 或实质段落保留率 < 75% 时回退原文。
3. 快速手动笔记默认不调用 LLM，改为用户显式请求 AI 建议。
4. 仅当用户要求「核心导读」时，在顶部生成导读，原文完整保留在下方。

**R（结果）**：相关投诉归零；保存 P95 延迟下降；用户开始愿意保存长文。

**可能的追问**：为什么是 90% / 75%？——阈值来自对历史草稿的人工抽查：低于 90% 时用户几乎必然感知到内容缺失；段落阈值用于捕捉「整体长度够但某段被删」的情况。阈值可配置，并持续用样本校准。

### Story 2：多级 Agent 传话筒（痛点 2）

**S**：Research 功能输出看起来很完整，但抽查三条结论有两条找不到原文依据。

**T**：让多级 Agent 的结论可追溯、可归因。

**A**：

1. 复现链路，定位到 planner 把「只看最近三个月」改写成「最近三篇」。
2. 引入共享证据层，交接传 capture/section ID，不再传自然语言摘要。
3. 定义结构化交接契约：目标、约束、证据 ID、推断范围、回退策略。
4. 评测加入证据保真率抽查，随机验证结论与来源。

**R**：证据可追溯率显著提升；错误能定位到具体阶段；团队不再盲目升级模型。

**追问**：结构化交接会不会限制模型发挥？——会限制「不该发挥」的部分，例如事实、数字和约束；在推断与表达层仍保留自由度。

### Story 3：130 秒延迟优化（痛点 3）

**S**：Research 管线经常打满 130 秒超时预算，用户在 30 秒内大量放弃。

**T**：在不明显降低质量的前提下，把延迟降到用户可接受范围。

**A**：

1. 分阶段打点，发现反思 + 二次修订占 45 秒，质量只提升 0.1 分。
2. 来源检索并行化，统一超时与降级。
3. 证据筛选分三层：规则去重、小模型粗筛、大模型精排。
4. 缓存稳定中间产物；按证据覆盖和置信度早停。

**R**：早期内部记录曾显示阶段耗时下降（未归档）；当前可复现的是轻量链路单例 21.3–27.2 秒（§8.11/§8.12，单例不是 P95）。Token -46%、评分 4.0 与二次交互率是早期内部记录，未归档评测产物，面试时标“待复核”，不当作当前证据。

**追问**：怎么避免早停漏证据？——用离线评测集校准阈值，并保留「用户要求更深入」的手动升级入口；高风险任务不早停。

### Story 4：从收藏夹到认知内化（痛点 4）

**S**：用户存了上千篇，但面试时仍说不清自己的观点。

**T**：设计一条从资料到卡片到专题的内化路径。

**A**：

1. 用户研究区分「收藏时刻」「理解时刻」「输出时刻」。
2. 资料层保真；卡片层只提炼可复用判断；专题层围绕长期问题组织。
3. 设计四类卡片模板（洞察/金句、新知/概念、方法/框架、避坑/边界）与图谱关系，支持从资料反查卡片、从专题反查证据。
4. 用 Golden Demo 数据集验证完整链路：6 篇资料、9 张卡片、3 个专题、36 条边（`scripts/seed_interview_demo.py` 输出）。

**R**：可用性测试中，用户能在 5 分钟内从一篇资料产出 1 张卡片，并说清它在专题中的位置。

**追问**：卡片会不会变成另一种收藏？——会，所以卡片必须有明确复用场景、边界和行动启发；没有复用价值的摘要不允许成为卡片。

### Story 5：意图路由与伴读（产品判断）

**S**：用户发来公众号链接问「这段什么意思」，系统却自动生成入库草稿，资料库被讨论内容污染。

**T**：让「讨论」和「保存」彻底分流。

**A**：

1. 定义四大意图：伴读解惑、好文收集、沉淀卡片、专题检索。
2. 伴读走 reading session，只保留临时上下文；保存才走 capture。
3. 在 Supervisor 中加入防传话筒铁律，禁止改写用户原文与 URL。
4. 对外统一「资料 / 卡片 / 专题」三个概念，减少术语噪音。

**R**：误入库率下降；用户更愿意用链接提问；资料库质量提升。

**追问**：如何判断意图？——材料 + 疑问句式优先判为伴读；材料 + 保存/提炼动作判为收集；讨论后 + 做成卡片判为沉淀；无新材料 + 问已有积累判为检索。不确定时短问一句。

### Story 6：RAG 检索防“旧笔记带偏”与 DeepSeek 原生联网搜索重构

**S**：在重构问答与联网系统时，面临三个问题：① 本地检索只搜长资料、漏了用户亲手沉淀的【卡片】，且搜专有名词（如 `MCP`、`130秒`）容易被纯向量检索漏掉；② 当问新问题时，向量检索硬凑出的弱相关旧笔记反而限制甚至带偏了大模型的回答（Context Distraction）；③ 联网搜索依赖重型插件与 4 种复杂模式按钮，用户选择成本高。

**T**：在不增加复杂调参黑盒的前提下，让本地检索更准、不被旧笔记绑架，并将联网搜索与前端交互做到极致精简。

**A**：

1. **复用整理切分 + 补齐卡片一等公民检索**：保留 `LibraryAgent` 自动生成 `##` 章节标题并与 `capture_indexer`（`identity` 概览层 + `section` 章节层）耦合的切分机制；将已采纳的【知识卡片（`garden_cards`）】作为独立完整单元纳入首层召回，并增加字面关键词精准命中兜底（不搞拍脑袋的多重加权系数）。
2. **防“知识库带偏”双保险（Relevance Gate + 开放式补全 Prompt）**：检索层设置最低向量相关度门槛（`MIN_VECTOR_SCORE = 0.46`，DashScope v4 标定值；0.20 是未标定的历史值，见 §8.9）并过滤已归档笔记；生成层摒弃“只能根据参考材料回答”的死板限制，改为「相关才引用（标 `[1][2]`）、局部覆盖不全时主动用通识补全、旧笔记片面时温和纠偏」。
3. **原生接入 DeepSeek 官方搜索接口 + 单开关极简交互**：弃用千问插件与多轮 Evidence Critic 审计，直接接入 `POST https://api.deepseek.com/v1/tools/search` 与 `/v1/tools/fetch`（直接利用官方 `rerank_score >= 1.5`、`authority` 与 `summary`）；前端砍掉 4 模式选择器，改为 DeepSeek 同款的单个 `[🌐 联网搜索]` 胶囊开关，并在底部来源用 `🗂️ 卡片` / `📄 资料` / `🌐 网页` 徽章自然溯源。

**R**：卡片与专有名词召回率显著提升，消除了弱相关笔记对回答质量的负向干扰，联网搜索响应速度与交互简洁度大幅改善。

## 六、风险与下一步

1. **真实嵌入质量**：Demo 向量只验证流程；生产需持续评估真实 embedding 的召回与成本。

### 8.2 检索消融（离线 hash post-fix：字面回归基线）

数据源：`docs/benchmark-rag-v3-offline-postfix.json`；报告：`docs/BENCHMARK-RAG-V3-offline-postfix.md`。语料 20 篇资料 / 86 chunk / 12 卡片 = 98 单元 / 28 条标注 Query（18 正 + 10 负）。

| 组 | Recall@3 | Recall@5 | MRR@5 | 负样本拦截 | P50 ms |
| --- | --- | --- | --- | --- | --- |
| G0 旧版：标题/摘要字面子串 | 0.389 | 0.389 | 0.389 | 10/10 | 0.06 |
| G1 仅两阶段向量 | 0.389 | 0.389 | 0.389 | 10/10 | 1.07 |
| G2 + 中文 FTS | 0.389 | 0.389 | 0.389 | 10/10 | 0.83 |
| G3 + 卡片召回与 1-hop | 0.389 | 0.389 | 0.361 | 10/10 | 1.49 |

**必须同时说出的三条限制**：
1. 本次运行的是离线字符哈希引擎（`char-ngram-blake2b-hash-1024`），它衡量字面重合，**不代表语义能力**。
2. G0 是修复 dispatcher 后的真实旧版字面基线，不是稻草人；在本离线引擎下四组打平，说明离线字符哈希分不出差异，不能据此宣称“语义检索带来提升”，也不能写“G0 < G1 < G2 < G3”。真实语义结论见 §8.2.1。
3. 这张表只代表离线 hash 引擎；真实语义结果见 §8.2.1。阈值不可跨引擎迁移。

阈值现状：代码与 `docs/calibration-dashscope.json` 均为 `MIN_VECTOR_SCORE = 0.46`（当前值）；`0.20` 是未标定的历史值。标定显示正负分布重叠（`separation = -0.0601`），单阈值只能做首轮粗筛，见 §8.9。

G3 的 MRR 略低于其它三组：卡片前置会把「相近但不对」的卡片顶到前面。这是卡片优先策略的真实代价，需要靠 `citation_count` 与来源数量继续调权，而不是假设卡片一定更好。

### 8.2.1 真实 DashScope 重跑（2026-11-16，当前语义口径）

数据源：`docs/benchmark-rag-v3-dashscope.json`；报告：`docs/BENCHMARK-RAG-V3-dashscope.md`。同一套语料：20 篇资料 / 86 chunk / 12 卡片 = 98 单元 / 28 条 Query（18 正样本 + 10 负样本）；引擎 `dashscope-text-embedding-v4`，阈值 `0.46`。

| 组 | Recall@3 | Recall@5 | MRR@5 | 负样本拦截 | P50 ms | P95 ms |
| --- | --- | --- | --- | --- | --- | --- |
| G0 旧版：标题/摘要字面子串 | 0.389 | 0.389 | 0.389 | 10/10 | 0.06 | 35.03 |
| G1 仅两阶段向量 | 0.833 | 0.833 | 0.806 | 9/10 | 1.22 | 19.48 |
| G2 + 中文 FTS | 0.833 | 0.833 | 0.806 | 9/10 | 1.70 | 2.63 |
| G3 + 卡片召回与 1-hop | 0.833 | 1.0 | 0.769 | 9/10 | 2.42 | 8.8 |

口径：

- G0 0.389 → G1/G2 0.833 → G3 1.0：真实语义 embedding 高于旧版字面基线，卡片语义召回又补上了 G1/G2 漏掉的卡片专属 query；这是本语料结论，换语料必须重跑。
- G1 = G2：中文 FTS 在这套 query 上没有带来额外 Recall；G3 Recall 提升到 1.0，但 MRR 0.769 < 0.806，卡片前置会把相近但不对的卡片顶前。不能简单写「层数越多越好」。
- 负样本 10 条：G0 拦 10/10，G1–G3 拦 9/10；q24 漏过 `cap_distractor_02`，不能写成 100%。
- 卡片专属 query（q10/q11/q12/q14/q15/q16）在 G3 的卡片级召回为 **6/6**。此前 benchmark 的 G3 调 `_search_garden_cards()` 时没传 query embedding，等价于只做字面匹配；修复后卡片语义召回才真正被测到。
- P50/P95 只含检索层，不含 embedding API 往返（计时前已预热缓存）和 LLM 合成。

### 8.3 口径修正：「130 秒」是超时预算，不是实测 P95

`bridge/research/types.py` 中的 `RESEARCH_ANSWER_TIMEOUT_SECONDS = 130` 是**超时上限**。面试中必须表述为：

> 旧管线的串行设计让单次请求经常打满 130 秒的超时预算；重构后用 `eval_research_quality.py` 的 `elapsed_ms` 记录分阶段耗时，按实测 P50/P95 汇报。

在跑出真实 P50/P95 之前，不要用「P95 130 秒」这个说法。当前可复现的轻量链路是单例 21.3–27.2 秒（§8.11/§8.12），只能说明量级，不是 P50/P95；完整分阶段耗时仍待重跑。

### 8.4 卡片排序结构半边：不要把卡片无条件置顶

早期结构实验（脚本 `scripts/eval_card_ordering_ab.py`，数值未归档为 JSON）显示：把卡片无条件提到第 1 位会把相关证据挤后（q01、q18 各降 1 位）。因此当前检索采用 evidence-first：先保证证据段覆盖，再按 `source_count` / `citation_count` 给卡片加权，而不是默认置顶。

这条结构观察与语义判官的定向结果一致：卡片前置会挤掉边界证据（见 §8.14，n=8，仅方向性）。

另一条实测限制：早期卡片的兜底召回是**字面匹配**，「卡片和资料怎么分工」这类转述问法召不回「三层分离」卡片（q10/q11/q12/q14/q15/q16 全部落空）。当前 V3.1 已把 `garden_cards.embedding` 接入 `_search_garden_cards()`，并使用独立的 `CARD_MIN_VECTOR_SCORE` 做粗筛；2026-11-16 重跑时发现 benchmark 的 G3 没传 query embedding，修复后这 6 条卡片目标的**卡片级召回为 6/6**。仍需注意：卡片召回成功不等于最终答案一定更好，G3 的 MRR 反而略低。

> 结构半边的具体 MRR 数字没有落成可引用 artifact，面试只引用“q01/q18 被挤后”的方向性观察；语义半边见 §8.14。

### 8.7 与 V3.0 Spec 的 3 处有意偏差（均在实现中验证过）

1. **20 篇评测语料放在 `scripts/eval_rag_benchmark.py`，没有塞进 `seed_interview_demo.py`**：demo 库要给人看，掺 14 篇提拉米苏/足球笔记会毁掉演示；评测语料独立构建，反而更可复现（`20 篇 / 86 chunk / 12 卡 / 98 单元`）。
2. **FTS 查询用 phrase 而不是 `AND`**：`"收敛 敛策 策略"` 要求 2-gram 连续，假阳性更少，成本相同。
3. **FTS 维护多了一层「开机自愈 + rebuild」**：只挂 `upsert` 无法覆盖存量库（`needs_reindex` 会跳过未变 chunk），实测迁移后 FTS=0；补上自愈后才达到 30=30。这条偏差本身就是本轮最有价值的发现。

链路⑤（写后图谱同步）已接线：`commit_reading_artifact` 与 `commit_garden_draft` 写卡完成后调用 `refresh_graph_after_write()`，异常吞掉不影响写操作；并有 `card_uses_capture` 边的单测锁死。

### 8.8 链路①写入侧（本轮补齐）

上一轮只建了 `capture_metadata.folder_path` 列却没有写入方，导致卡片继承专题永远拿到 `Inbox`。本轮补齐：

- 索引/重索引时把 frontmatter 的 `folder_path`（或 `folder`）镜像进 `capture_metadata`（`LibraryAgent._sync_capture_folder`）；
- `create_garden_card()` 在写入后按 `capture_ids` 依次查 `capture_metadata.folder_path`，写入 `garden_cards.source_theme`；
- 前端因此**不需要**再传 `source_theme`：继承发生在服务端，客户端不参与，避免伪造。

单测锁死：`test_capture_folder_mirrors_frontmatter_and_card_inherits_theme`（资料 `AI 产品面试` → 卡片 `source_theme == AI 产品面试`）。

### 8.9 DashScope 检索重跑：已完成（2026-11-16）

2026-11-16 已用修复后的 dispatcher + `text-embedding-v4` 完成真实重跑，结果见 §8.2.1：G0 0.389，G1/G2 0.833，G3 1.0，负样本 G0 10/10、G1–G3 9/10。旧报告里的四组 0.833 仍然不能引用——那是 G0 误走 G3 的调度 bug；新的 G1/G2 0.833 与 G3 1.0 是修复后的真实成绩，引用时必须指向 2026-11-16 重跑后的 `docs/benchmark-rag-v3-dashscope.json`。

可以说的：

- 在这套 28 条 query 上，语义 embedding 相对旧版标题/摘要子串把 Recall@5 从 0.389 提到 0.833（G1/G2），卡片语义召回把 G3 提到 1.0；
- 负样本 G0 10/10、G1–G3 9/10（q24 漏过一条）；
- G3 的 MRR 反而略低（0.769 vs 0.806），卡片前置会挤掉部分证据排序。

不能说的：

- “旧版 0.5 → 新版 0.833”：旧版真实基线是 0.389，0.5 是更早的残缺 G0；
- “G0 < G1 < G2 < G3”：G1=G2=G3 的 Recall 相同，G3 的 MRR 更低；
- 外推到其他语料或真实用户问题分布。

阈值标定仍是独立证据（`docs/calibration-dashscope.json`，直接对 embedding 分数做统计，不经过 G0 dispatcher）：

- 30 组正样本 P10 = 0.4286，168 组负样本 P95 = 0.4887，`separation = -0.0601`，正负分布重叠；
- 建议工作点与当前代码值均为 `0.46`；`0.20` 是历史未标定值；
- 单阈值只能做首轮粗筛，生产上仍需 rerank 或分数融合。

结论：**0.46 是当前代码值；真实重跑在这套小语料上支持“语义召回优于字面基线”，但不支持“层数越多越好”，也不足以证明线上答案质量。**

### 8.10 实验 5 的新阻塞（不是凭证问题）

2026-11-15 凭证可用时，运行 `python scripts/eval_research_quality.py --live --canary --json`，在第一个 case 启动时报：

```
PermissionError: [WinError 5] 拒绝访问。
  File "multiprocessing/connection.py", line 575, in Pipe -> _winapi.CreateFile
```

原因是评测脚本用 `multiprocessing.Queue` 做超时隔离，而本机 DSH 沙箱禁止子进程打开命名管道（已记录的平台边界）。**代码与 key 都没问题，是执行环境限制**；换到普通终端（非沙箱）或去掉超时 wrapper 即可跑出阶段耗时。

### 8.11 实验 5：真实联网管线单例实测（2026-11-15）

`--live --canary --limit 1 --case-timeout 0`（`--case-timeout 0` 走进程内串行，绕过沙箱禁止命名管道的问题）：

| 指标 | 实测值 |
| --- | --- |
| 端到端耗时 | **27.2 s** |
| 搜索阶段 | 6.1 s（search_backend = deepseek） |
| 候选 / 采纳 | 30 / 6 |
| 抽取状态 | 6 条全部 `summary`，0 条 full fetch |
| 用例判定 | `passed=False`（质量断言未过，见 failures） |

这说明两件事：一是轻量链路的**端到端确实落在 20~30 秒量级**，不再是 130 秒；二是**摘要优先策略真的跳过了全部正文抓取**，和阈值标定暴露的问题一样，属于"延迟降了、但证据强度下降"的同一类权衡，需要按问题类型区分（概念题可只吃摘要，需要论证的题必须 fetch）。

口径：单例实测，不是 P95；要 P95 需跑完整 canary（5 例）或普通终端下跑全量。

失败断言（原文）：

```
rejected web sources below minimum: 0 < 1
reliable adopted web sources below minimum when answered: 0 < 1
```

即：摘要优先把 30 个候选全部"采纳为摘要"，一个都不拒绝，于是 (a) 没有 rejected 源、(b) 没有"可靠（正文已抓取）"源，两层证据门槛都不过。这是**摘要优先策略与证据契约的冲突**，属于需要修的真实问题，不是评测脚本的毛病。

### 8.12 对 8.11 诊断的更正（实测复核）

给"摘要优先"加了"至少抓 1 篇作为可信锚点"的修复后重跑同一用例：`elapsed 21.3s`、`extract_status={'summary': 4}`，两条断言**仍然失败**。

更正结论：
- 命中"不抓正文"的分支不是 `_summary_only_is_enough`，而是更早的 `_local_concept_summary_mode`（概念题专用）。我的修复对概念题不生效——**该修的是否要让概念题也抓 1 篇，是产品取舍，不是 bug**。
- `rejected web sources below minimum: 0 < 1` 在轻量链路上**结构上无法满足**：轻链路砍掉了 Evidence Critic，根本不存在"被拒绝的源"。这条断言属于 legacy 七阶段管线的质量契约，**不适用于轻量路径**——是 case 契约与路径的不匹配，我之前判定为"产品 Bug"是错的。
- 结论：`eval_research_quality.py` 的 canary case 需要按路径区分契约（legacy 要求 rejected≥1，light 不应要求）；轻链路可信度锚点应改为"要求 reliable≥1 且 summary 来源标注为 secondary"。


### 8.13 实验 2 语义半边：第一版为什么测不出东西（历史）

早期 `scripts/eval_card_ordering_judge.py` 用 12 条 query 跑出 card_first 与 evidence_first 的 boundary_rate 均为 0.0。原因有两层：一是 benchmark 的 12 张卡片都是一句话结论，原文没有对应的“边界/前提”段落，没有边界可指出；二是判官 `max_tokens` 太小，模型返回空串，判分恒为 NO。

这条结果只作为“执行链路和判官都需要修”的历史记录，不能引用为“卡片前置更好/更差”的结论。修正后的结果见 §8.14。

### 8.14 实验 2 语义半边：对抗语料下的定向结果（n=8）

重写 `scripts/eval_card_ordering_judge.py`：每个主题构造“卡片片面 vs 原文有边界”的对抗对，上下文限 4 条，唯一变量是排序。产物：`docs/card-ordering-judge.json`。

| 排序 | 指出边界的比例 |
| --- | --- |
| 卡片优先（card + 3 段） | **5/8 = 0.625** |
| 证据优先（4 段，含边界段） | **8/8 = 1.0** |

方向与结构实验一致：卡片优先会挤掉边界证据。但必须说清三个限制：

1. **n=8，仍只能算方向性信号**，不能报强比率结论；
2. **单次判官、单一模型**，没有多人标注或重复判分；
3. 即使边界段在上下文里，证据优先也只有 8/8 这一次小样本结果；生产结论需要更大样本并做判官一致性检查。

历史口径：更早的 `0/4 vs 1/4` 是判官预算 bug 下的结果，已作废；不要再用。
